# 自编代码中文注释设计

## 1. 目标

为SmartHood项目的自编代码补充结构化中文注释，使用户能够直接从源码理解模块职责、函数接口、关键数据、硬件时序、任务流程和错误处理，同时保证固件行为完全不变。

以后新增或修改的自编代码继续遵守同一注释规范。助手给出代码时，同时说明实现流程、采用该方案的原因、关键参数和容易出错的位置。

## 2. 修改范围

需要补充中文注释的文件包括：

```text
firmware/SmartHood/App/Inc/app_tasks.h
firmware/SmartHood/App/Inc/debug_log.h
firmware/SmartHood/App/Src/app_tasks.c
firmware/SmartHood/App/Src/debug_log.c

firmware/SmartHood/BSP/Inc/bsp_dht11.h
firmware/SmartHood/BSP/Inc/bsp_st7735s.h
firmware/SmartHood/BSP/Inc/fonts.h
firmware/SmartHood/BSP/Src/bsp_dht11.c
firmware/SmartHood/BSP/Src/bsp_st7735s.c
firmware/SmartHood/BSP/Src/fonts.c
```

`Core/Src/freertos.c`只允许在CubeMX的`USER CODE`区域内补充中文注释，解释DebugLog初始化、默认任务委托和传感器任务委托。其他Core文件只有在存在项目自编`USER CODE`时才补充，不修改CubeMX生成区。

以下内容不修改：

- STM32 HAL和LL驱动源码。
- CMSIS与FreeRTOS中间件源码。
- CubeMX自动生成区域、启动文件和设备支持文件。
- Keil设备包代码。
- 字模数组的每个字节。

## 3. 注释风格

采用结构化中文注释，不进行机械式逐行翻译。

### 3.1 文件与模块

每个自编头文件和源文件说明：

- 所属层次，例如App或BSP。
- 模块负责什么。
- 模块依赖哪些外设或服务。
- 模块不负责什么，避免职责混淆。

### 3.2 类型和宏

枚举、结构体、宏和常量需要说明：

- 物理单位，例如μs、ms、像素和扩大10倍的数值。
- 数值来源，例如DHT11协议或ST7735S命令。
- 安全边界，例如超时阈值、坐标范围和缓冲区长度。

### 3.3 函数接口

公开函数使用以下形式：

```c
/**
 * @brief 函数作用。
 * @param 参数名称 参数含义。
 * @return 返回值及成功/失败条件。
 */
```

无参数或无返回值时省略无意义字段。内部静态函数可以使用较短的块注释，但必须解释关键前置条件和输出效果。

### 3.4 函数内部

只在下列位置增加注释：

- 一组语句共同完成一个明确阶段时。
- 实现原因不能从语句本身直接看出时。
- 涉及硬件时序、坐标变换、中断状态或并发保护时。
- 错误出口需要恢复硬件/内核状态时。

不添加“变量加一”“调用函数”“返回结果”等重复代码表面的注释。

## 4. 各模块重点

### 4.1 DebugLog

- 为什么在任务创建前初始化互斥量。
- 为什么格式化和UART发送需要由同一把锁保护。
- 缓冲区截断策略和100 ms发送超时。
- 未初始化或互斥量获取失败时的行为。

### 4.2 App Tasks

- 默认任务启动显示自检及1秒心跳流程。
- SensorTask的2秒上电等待与周期读取流程。
- DHT11状态到串口日志的映射。
- 扩大10倍整数如何转成一位小数文本。

### 4.3 DHT11

- PD0开漏输出与输入上拉切换。
- TIM5 1 MHz计数器和无符号差值的溢出兼容性。
- 18 ms启动低电平、30 μs释放等待、120 μs边沿超时和50 μs位判断阈值。
- 为什么只在协议关键区间屏蔽中断。
- 40位数据组合、校验和、负温度和只在成功时更新输出。
- 所有错误路径必须恢复中断和GPIO状态。

### 4.4 ST7735S

- SPI2阻塞发送、CS/DC/RST/BLK控制。
- ST7735S命令与数据的区别。
- 地址窗口、X/Y偏移、竖屏尺寸和RGB565字节顺序。
- 像素、矩形、全屏和5×7文本绘制的边界处理。
- MADCTL=0xC0的方向与颜色校准依据。

### 4.5 字模

- 5×7 ASCII字模的字符范围。
- 每列或每行的位排列方式。
- 字符索引和未知字符处理。
- 不逐字节解释字形数据。

## 5. 编码和工具兼容性

源码中文注释统一保存为UTF-8。批量修改前先选取一个小文件进行试验，并在Keil μVision 5.24与ARMCC 5.06中确认：

- 中文显示可读。
- 编译器不报告非法字符或编码警告。
- 文件换行结尾正常。

如果Keil编辑器显示乱码，优先调整编辑器显示/保存编码，不将工程拆分为UTF-8与GBK混合编码。

## 6. 实施顺序

1. 记录注释前固件Program Size和HEX哈希。
2. 选择小型头文件进行UTF-8中文注释试验并编译。
3. 注释App模块并编译。
4. 注释DHT11模块并编译。
5. 注释ST7735S与字模模块并编译。
6. 注释`freertos.c`的USER CODE区域并全量重编译。
7. 比较注释前后的Program Size和HEX哈希。
8. 在Keil中抽查中文显示，运行M1/M2回归，再继续M3A未连接TIMEOUT测试。

注释由助手在共享工程中进行，用户负责在Keil中检查中文显示、执行编译和观察硬件现象。全部Git操作仍由助手完成。

## 7. 验收标准

- 只修改注释、空白和必要的文件编码，不修改任何可执行语句、声明含义或数据值。
- Keil全量构建为0 Error(s)、0 Warning(s)。
- Program Size保持：Code=24002、RO-data=1286、RW-data=156、ZI-data=39524。
- 在构建工具保持不变的条件下，HEX文件哈希应保持一致；若不一致，必须先检查源码是否存在非注释差异，再继续。
- Keil中抽查中文注释能够正常显示。
- PA0、PA1、USART1和ST7735S行为保持不变。
- M3A TIMEOUT硬件测试在注释改造通过后恢复执行。

## 8. 后续代码要求

以后助手提供的所有自编代码必须：

1. 使用同一套结构化中文注释。
2. 在代码后给出从入口到输出的执行流程。
3. 解释关键设计选择和参数来源。
4. 指出硬件接线、时序、并发和错误恢复中的易错点。
5. 避免注释与代码含义重复，避免失效注释。
